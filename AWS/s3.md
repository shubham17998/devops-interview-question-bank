# S3 Interview Questions

## Basics
Q: What is Amazon S3?
Ans: Simple Storage Service — AWS's object storage service, offering virtually unlimited, durable (11 nines), highly available storage accessed via a simple REST/HTTP API, organized as buckets containing objects.

Q: What is a Bucket?
Ans: A top-level container for objects in S3, with a globally unique name (across all of AWS, not just your account), a region, and its own access policies/configuration.

Q: What is an Object?
Ans: The fundamental entity stored in S3 — data (the file content) plus metadata (content-type, custom key-value metadata) plus a unique key, stored within a bucket.

Q: What is an Object Key?
Ans: The unique identifier for an object within a bucket — essentially its full "path" (e.g., `images/2024/photo.jpg`). S3 is technically a flat key-value store; folder-like hierarchies are just a UI/convention built from `/` characters in keys.

## Versioning & Replication
Q: What is Versioning?
Ans: A bucket setting that, once enabled, keeps every version of an object whenever it's overwritten or deleted (a delete just adds a "delete marker" rather than removing data), protecting against accidental overwrites/deletions and enabling recovery of prior versions.

Q: What is the difference between current version and previous version in S3?
Ans: The **current version** is what's returned by default on a GET request (the latest, or the version pointed to if no delete marker is on top). **Previous/noncurrent versions** are earlier versions retained by versioning, retrievable only by explicitly specifying their version ID.

Q: How do you delete S3 object versions when versioning is enabled?
Ans: A normal `DeleteObject` just adds a delete marker (soft delete — the version is retained, just hidden from default listing/GET). To permanently remove a specific version, issue `DeleteObject` with that version's explicit `versionId` — this is the only way to truly purge data under versioning.

Q: Can lifecycle policies be used to clean up old S3 versions?
Ans: Yes — a lifecycle rule with a `NoncurrentVersionExpiration` action can automatically permanently delete noncurrent versions after a specified number of days, preventing unbounded storage growth from versioning.

Q: What is Cross-Region Replication?
Ans: A bucket-level feature (CRR) that automatically, asynchronously copies new objects (and optionally existing ones) from a source bucket to a destination bucket in a different region — used for disaster recovery, latency reduction, or compliance requirements. (Same-Region Replication, SRR, is the equivalent within one region.)

## Lifecycle & Storage Classes
Q: What is S3 Lifecycle Policy?
Ans: A set of rules attached to a bucket (or prefix) that automatically transitions objects between storage classes or expires/deletes them based on age, reducing storage costs without manual intervention.

Q: What are S3 Lifecycle Rules?
Ans: Individual rules within a lifecycle policy, each scoped by prefix/tag filter, specifying transition actions (e.g., "move to Standard-IA after 30 days, Glacier after 90 days") and/or expiration actions (e.g., "delete after 365 days").

Q: How do Lifecycle Rules work?
Ans: S3 evaluates each object nightly against the bucket's lifecycle rules based on the object's age (or a specific date), and automatically performs the configured transition or expiration action — no manual intervention required once configured.

Q: What actions can be performed through Lifecycle Rules?
Ans: Transition to a cheaper storage class (Standard-IA, One Zone-IA, Intelligent-Tiering, Glacier, Glacier Deep Archive), expire (permanently delete) current object versions, expire noncurrent versions, and clean up incomplete multipart uploads.

Q: What are the S3 Storage Classes?
Ans: Standard, Intelligent-Tiering, Standard-IA, One Zone-IA, Glacier Instant Retrieval, Glacier Flexible Retrieval, Glacier Deep Archive, and Reduced Redundancy Storage (legacy, deprecated).

Q: Difference between S3 Standard and Standard-IA?
Ans: Both offer the same durability/availability SLA and millisecond access, but **Standard-IA** (Infrequent Access) has a lower storage price with a retrieval fee per GB and a 30-day minimum storage duration — designed for data accessed occasionally, not for frequently-read data (where it'd cost more overall than Standard).

Q: Difference between Standard-IA and One Zone-IA?
Ans: Standard-IA replicates data across at least 3 Availability Zones (same durability as Standard). One Zone-IA stores data in only a single AZ — cheaper, but data is lost if that AZ is destroyed; suitable only for easily reproducible data or secondary copies.

Q: What is Intelligent-Tiering?
Ans: A storage class that automatically monitors access patterns per object and moves it between frequent-access and infrequent-access (and optionally archive) tiers, without retrieval fees for the standard tiers — useful when access patterns are unpredictable and you don't want to manage lifecycle rules manually.

Q: When should Glacier be used?
Ans: For archival data that's rarely accessed but must be retained (compliance, backups, historical logs), where retrieval can tolerate minutes-to-hours of latency in exchange for very low storage cost.

Q: When should Glacier Deep Archive be used?
Ans: For the coldest, least-accessed data (e.g., regulatory archives kept for 7+ years) where retrieval can tolerate up to ~12 hours, in exchange for the lowest storage cost S3 offers.

Q: How do you retrieve an object from Glacier?
Ans: Initiate a restore request (`RestoreObject` API or console "Initiate Restore"), choosing a retrieval tier (Expedited ~1-5 min, Standard ~3-5 hrs, Bulk ~5-12 hrs for Glacier Flexible Retrieval; Standard/Bulk only, up to 12/48 hrs for Deep Archive) — this temporarily creates a restored copy accessible for a duration you specify, after which it reverts to Glacier-only.

Q: How do you optimize storage costs using S3?
Ans: Use lifecycle rules to transition aging data to cheaper classes automatically, use Intelligent-Tiering for unpredictable access patterns, enable `NoncurrentVersionExpiration` to bound versioning growth, clean up incomplete multipart uploads via lifecycle rules, use S3 Storage Lens/Cost Explorer to identify waste, and compress objects where practical.

## Security & Access
Q: How do you secure an S3 bucket?
Ans: Enable Block Public Access at the account/bucket level, use bucket policies/IAM for least-privilege access, enable encryption (SSE-S3/SSE-KMS) by default, require TLS via a bucket policy condition (`aws:SecureTransport`), enable versioning + MFA delete for critical buckets, enable access logging/CloudTrail data events, and use Access Points for scoped access patterns.

Q: How does an EC2 instance securely access S3?
Ans: Via an IAM role attached through an instance profile — the instance's SDK/CLI automatically retrieves temporary credentials scoped to that role from the Instance Metadata Service, avoiding any hardcoded access keys.

Q: How do you give temporary access to a private S3 object?
Ans: Generate a **pre-signed URL** (`aws s3 presign` or SDK `getSignedUrl`), which embeds a signature and expiration into the URL, letting anyone with the link access that specific object until it expires — without making the bucket/object public.

Q: How do you provide cross-account S3 access?
Ans: Attach a bucket policy granting the other account's principal access, or create an IAM role in the bucket's account that the other account can assume (`sts:AssumeRole`) with S3 permissions attached.

Q: How do you provide S3 access to 10 users from another account?
Ans: Create a single cross-account IAM role with the needed S3 permissions, and have those 10 users (or a group/role representing them in the other account) assume it — far more scalable than 10 individual grants.

Q: Bucket Policy vs IAM Role for cross-account access?
Ans: Bucket policies are resource-based and simpler for direct, static external-account grants. IAM roles require explicit assumption, issue temporary credentials, and are easier to audit/revoke centrally — generally preferred for anything beyond simple, few-principal access.

Q: What is the best scalable approach for multi-user S3 access?
Ans: Role-based access: define IAM roles per access pattern, have users/applications assume the appropriate role, rather than managing per-user policies or bucket policy statements that grow unmanageably as user count increases.

Q: Can CloudFront work with a private S3 bucket?
Ans: Yes — via Origin Access Control (OAC), which lets CloudFront read from an otherwise fully private bucket, forcing all access through CloudFront.

Q: What is a Signed URL?
Ans: A time-limited, signed link (from CloudFront or S3) granting access to one specific object without making it publicly accessible.

Q: What is a Signed Cookie?
Ans: Similar to a signed URL, but grants access to multiple restricted resources (e.g., a whole private content library) via a cookie set on the client, rather than signing each URL individually.

## Static Website Hosting
Q: How do you build a static website using S3?
Ans: Enable Static Website Hosting on the bucket, set an index document (and optional error document), upload the site's HTML/CSS/JS as objects, and either make the bucket public (with a bucket policy for `s3:GetObject`) or — better — put CloudFront in front with OAC so the bucket stays private and you get HTTPS/caching for free.

Q: How do you increase availability of an S3 website across regions?
Ans: Enable Cross-Region Replication to a bucket in a second region, put Route53 with a failover or latency-based routing policy (with health checks) in front of both regions' endpoints (or CloudFront origin groups with origin failover), so traffic automatically shifts if the primary region/bucket becomes unavailable.

## Logging, Encryption & Performance
Q: What is the difference between S3 object-level and bucket-level logging? How do you enable logging for a bucket?
Ans: **Bucket-level (server access) logging** records request-level details (requester, time, action, key, response) for all requests to a bucket, delivered as log files to a target bucket — enabled via bucket Properties → Server access logging. **Object-level logging** refers to fine-grained data events (`GetObject`, `PutObject`, etc.) captured via CloudTrail data events, giving richer detail (e.g., for security auditing) at higher cost, enabled per-bucket/prefix in a CloudTrail trail's data event configuration.

Q: How do you secure S3 data at rest and in transit? What are the options for encrypting objects and configuring SSL/TLS for data transfer?
Ans: **At rest:** SSE-S3 (AWS-managed keys, default and free), SSE-KMS (customer-managed KMS keys, adds audit trail via CloudTrail and access control via key policy), SSE-C (customer-supplied keys, AWS doesn't store the key), or client-side encryption before upload. **In transit:** enforce HTTPS/TLS by denying requests where `aws:SecureTransport` is false in the bucket policy; S3 supports TLS 1.2+ on all endpoints by default.

Q: How do you optimize S3 performance? Discuss techniques such as multipart uploads, S3 Transfer Acceleration, and S3 Select.
Ans: **Multipart uploads** split large objects into parts uploaded in parallel (recommended for objects >100MB, required above 5GB), improving throughput and allowing resumable uploads on failure. **S3 Transfer Acceleration** routes uploads through CloudFront edge locations to reach S3 over AWS's optimized backbone network, speeding up long-distance uploads. **S3 Select** lets you retrieve only a filtered subset of data (via SQL-like expressions) from a CSV/JSON/Parquet object, reducing data transferred and processing time instead of pulling the whole object client-side.

Q: What are S3 event notifications, and how can you use them to trigger actions when objects are uploaded, modified, or deleted?
Ans: A bucket feature that publishes events (e.g., `s3:ObjectCreated:*`, `s3:ObjectRemoved:*`) to a destination — Lambda, SQS, or SNS — whenever matching activity occurs on objects (optionally filtered by prefix/suffix). Commonly used to trigger a Lambda function to process an uploaded file (e.g., generate a thumbnail, kick off an ETL job) automatically without polling.
